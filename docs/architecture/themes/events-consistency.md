# Events and consistency (cross-cutting) — explorer card

- Scope: theme — integration events, publishing reliability, duplicates/failures/ordering, data consistency across Catalog, Basket, Ordering, OrderProcessor, PaymentProcessor, Webhooks, WebApp, Identity and the platform libraries (src/, excluding src/ClientApp and src/HybridApp)
- Claim prefix: EVT
- Verified at commit: d9aa12b

## Responsibility
This card answers how services talk through RabbitMQ integration events, how publishing is made reliable, and where state can drift. The order flow is a choreographed saga: Ordering owns order state, Catalog validates stock, PaymentProcessor simulates payment, OrderProcessor times the grace period. Reliability is partial: the transactional outbox is written correctly, but nothing re-sends failed events and consumers drop failed messages.

## Public interface
Not applicable to this theme. The only "interface" is the event bus contract.
- [EVT-01] Bus contract: `IEventBus.PublishAsync` publishes to one direct exchange `eshop_event_bus`, routing key is the event class short name, delivery mode persistent, `mandatory: true` — `src/EventBusRabbitMQ/RabbitMQEventBus.cs:31-33,47-49,75-77,97-102`
- [EVT-02] Every subscriber declares its own durable queue named by `EventBus:SubscriptionClientName` and binds it once per subscribed event name; each service therefore gets its own copy of every event, and replicas of one service compete on the same queue — `src/EventBusRabbitMQ/RabbitMQEventBus.cs:258-285`
- [EVT-03] The event envelope carries only `Id` (Guid) and `CreationDate`; there is no version, sequence number, correlation or causation ID — `src/EventBus/Events/IntegrationEvent.cs:8,12,15`

## Data
- [EVT-04] The outbox table `IntegrationEventLog` lives in each owning service's own database (Ordering and Catalog use it), row key is the event's `Id`, with State (NotPublished, InProgress, Published, PublishedFailed), TimesSent, Content JSON and TransactionId — `src/IntegrationEventLogEF/IntegrationEventLogEntry.cs:13-19,21-33`, `src/IntegrationEventLogEF/EventStateEnum.cs:5-8`
- [EVT-05] Only Ordering and Catalog use the outbox. `RetrieveEventLogsPendingToPublishAsync` has a single caller, in Ordering — `src/Ordering.API/Application/IntegrationEvents/OrderingIntegrationEventService.cs:15`, `src/Catalog.API/IntegrationEvents/CatalogIntegrationEventService.cs:28-40`
- [EVT-06] Ordering's idempotency table `ClientRequest` stores request IDs for HTTP commands only (create, cancel, ship). It is not used for integration events — `src/Ordering.Infrastructure/Idempotency/RequestManager.cs:13-37`, `src/Ordering.API/Application/Commands/CreateOrderCommandHandler.cs:57-71`
- [EVT-07] Data duplicated across services by design: Basket stores only product id and quantity, and WebApp rehydrates name and price from Catalog on each read; Ordering copies product name, price and picture into order items at checkout — `src/WebApp/Services/BasketState.cs:123`, `src/Ordering.API/Application/Commands/CreateOrderCommandHandler.cs:42-45`
- [EVT-08] OrderProcessor reads Ordering's `ordering.orders` table directly with raw SQL (a shared-database coupling outside the event contract) — `src/OrderProcessor/Services/GracePeriodOrdersRepository.cs:24-28`

## Patterns and risks seen in the code

Publishing reliability
- [EVT-24] Ordering writes the outbox row inside the command's DB transaction: `AddAndSaveEventAsync` calls `SaveEventAsync` with the current transaction — `src/Ordering.API/Application/IntegrationEvents/OrderingIntegrationEventService.cs:36-41`, `src/IntegrationEventLogEF/Services/IntegrationEventLogService.cs:34-44`
- [EVT-25] Domain events are dispatched before `SaveChanges`, so domain event handlers (and their outbox rows) commit atomically with the aggregate change — `src/Ordering.Infrastructure/OrderingContext.cs:47-59`
- [EVT-26] `TransactionBehavior` commits, then calls `PublishEventsThroughEventBusAsync(transactionId)` in the same request. Mediator-sent commands from integration event handlers go through the same behavior, so they publish too — `src/Ordering.API/Application/Behaviors/TransactionBehavior.cs:43-52`, `src/Ordering.API/Extensions/Extensions.cs:39-41`
- [EVT-27] Catalog saves business changes and the outbox row in one resilient local transaction, then publishes directly — `src/Catalog.API/IntegrationEvents/CatalogIntegrationEventService.cs:28-40`
- [EVT-28] Risk: no relay or retry. A publish failure only marks the row PublishedFailed; the pending query selects only NotPublished rows of a given TransactionId and has no other caller. A crash between commit and publish, or a failed publish, leaves the event unsent forever (the TransactionId filter means even an unsent NotPublished row is not picked up later) — `src/Ordering.API/Application/IntegrationEvents/OrderingIntegrationEventService.cs:21-32`, `src/IntegrationEventLogEF/Services/IntegrationEventLogService.cs:19-24`, `src/Catalog.API/IntegrationEvents/CatalogIntegrationEventService.cs:21-25`
- [EVT-29] Risk: the publish call has no publisher confirms. `BasicPublishAsync` with `mandatory: true` has no return handler here, so an unroutable message (no queue bound) is not detected. The row is marked Published once `PublishAsync` returns. Retry only covers BrokerUnreachableException and SocketException — `src/EventBusRabbitMQ/RabbitMQEventBus.cs:97-102,302-310`
- [EVT-30] Risk: OrderProcessor and PaymentProcessor publish directly, with no outbox, so a crash or failure after their input loses the output (for PaymentProcessor the event that triggered it is already acked) — `src/OrderProcessor/Services/GracePeriodManagerService.cs:60`, `src/PaymentProcessor/IntegrationEvents/EventHandling/OrderStatusChangedToStockConfirmedIntegrationEventHandler.cs:32`
- [EVT-31] Risk: in Catalog's stock handlers the outbox is saved and published in the same handler call, but the event ID is used as the row ID. If the handler is redelivered, a new event object (new Id) is created, so downstream sees a second, differently identified event — `src/Catalog.API/IntegrationEvents/EventHandling/OrderStatusChangedToAwaitingValidationIntegrationEventHandler.cs:27-32`, `src/EventBus/Events/IntegrationEvent.cs:8`

Failures on the consumer side
- [EVT-32] Risk: consumer errors are logged and the message is acked regardless ("Even on exception we take the message off the queue"), with no dead-letter exchange and no consumer-side retry. A handler that throws means the event is permanently lost — `src/EventBusRabbitMQ/RabbitMQEventBus.cs:170-180`
- [EVT-33] Handlers for one event run sequentially. If the first of several handlers throws, later handlers in that process are skipped, and the whole message is acked anyway — `src/EventBusRabbitMQ/RabbitMQEventBus.cs:204-207`
- [EVT-34] Risk: unknown event name or unresolvable type is logged and dropped, then acked — `src/EventBusRabbitMQ/RabbitMQEventBus.cs:192-196`
- [EVT-35] Risk: the consumer starts on a background task; if the connection is not open it returns silently, so the host runs without consuming and nothing is retried — `src/EventBusRabbitMQ/RabbitMQEventBus.cs:229-239`
- [EVT-36] Risk: a message body containing "throw-fake-exception" throws in the production consumer path (and is then acked and dropped) — `src/EventBusRabbitMQ/RabbitMQEventBus.cs:163-166`
- [EVT-37] Catalog Paid handler: `RemoveStock` throws when `AvailableStock == 0`; the loop aborts at the first such item and `SaveChangesAsync` is not reached, so stock for the whole order is not decremented. Combined with EVT-32, the decrement is lost and not retried — `src/Catalog.API/IntegrationEvents/EventHandling/OrderStatusChangedToPaidIntegrationEventHandler.cs:13-20`, `src/Catalog.API/Model/CatalogItem.cs:62-67`
- [EVT-38] Webhooks: `SendAll` posts with `Task.WhenAll`, no retry, status codes not checked, no timeout; a throwing receiver faults the handler, and delivery to other receivers is not guaranteed to complete before the message is acked — `src/Webhooks.API/Services/WebhooksSender.cs:5-11,32`

Duplicates (at-least-once)
- [EVT-39] The library offers at-least-once semantics with no dedup or inbox: `TimesSent` is incremented but never checked, and consumers get no event-ID check — `src/IntegrationEventLogEF/Services/IntegrationEventLogService.cs:61-70`, `src/EventBusRabbitMQ/RabbitMQEventBus.cs:183-208`
- [EVT-40] OrderProcessor republishes `GracePeriodConfirmed` for every Submitted order older than the grace period on every 30 s poll, with no marker of what it already sent. Ordering stays safe because `SetAwaitingValidationStatus` only acts when status is Submitted, but every duplicate still runs a full command and transaction — `src/OrderProcessor/Services/GracePeriodManagerService.cs:50-60`, `src/OrderProcessor/Services/GracePeriodOrdersRepository.cs:24-28`, `src/Ordering.API/Application/IntegrationEvents/EventHandling/GracePeriodConfirmedIntegrationEventHandler.cs:19-28`, `src/Ordering.Domain/AggregatesModel/OrderAggregate/Order.cs:99-106`
- [EVT-41] Ordering's status commands from integration events are sent as plain commands (`mediator.Send(command)`), not wrapped in `IdentifiedCommand`, so the request-ID dedup is not used for event-driven paths. Dedup comes only from the aggregate's state guards — `src/Ordering.API/Application/IntegrationEvents/EventHandling/OrderPaymentSucceededIntegrationEventHandler.cs:12-21`, `src/Ordering.API/Application/IntegrationEvents/EventHandling/OrderStockConfirmedIntegrationEventHandler.cs:12-21`
- [EVT-42] Duplicate Paid event is harmful to Catalog: `OrderStatusChangedToPaid` is handled by decrementing stock with no record of which order was processed, so a redelivery decrements again. Ordering's guard prevents a second Paid event from being raised, but the bus itself can still redeliver an unacked message — `src/Catalog.API/IntegrationEvents/EventHandling/OrderStatusChangedToPaidIntegrationEventHandler.cs:13-20`
- [EVT-43] Duplicate `OrderStatusChangedToAwaitingValidation` makes Catalog emit another StockConfirmed or StockRejected (idempotent read-only check, new event Id each time); Ordering ignores it unless status still matches — `src/Catalog.API/IntegrationEvents/EventHandling/OrderStatusChangedToAwaitingValidationIntegrationEventHandler.cs:15-32`, `src/Ordering.Domain/AggregatesModel/OrderAggregate/Order.cs:108-117`
- [EVT-44] Webhooks has no dedup: a redelivered Paid or Shipped event posts the hook to every subscriber again — `src/Webhooks.API/IntegrationEvents/OrderStatusChangedToPaidIntegrationEventHandler.cs:8-17`
- [EVT-45] Basket handler on duplicate `OrderStarted` just deletes the basket again, which is idempotent for the same user, but it also deletes any basket the user has built since the first delivery — `src/Basket.API/IntegrationEvents/EventHandling/OrderStartedIntegrationEventHandler.cs:14`
- [EVT-46] HTTP-level idempotency: the request ID is stored before the command runs and any exception returns `default` (false). A retry with the same ID returns true (duplicate), so a failed create/cancel/ship can look successful — `src/Ordering.API/Application/Commands/IdentifiedCommandHandler.cs:41-48,99-102`, `src/Ordering.API/Application/Commands/CreateOrderCommandHandler.cs:67-70`

Out-of-order delivery
- [EVT-47] Events carry no sequence or version. Order status guards turn out-of-state events into silent no-ops for AwaitingValidation, StockConfirmed and Paid (the order stays where it is), and into exceptions for Shipped and Cancelled — `src/Ordering.Domain/AggregatesModel/OrderAggregate/Order.cs:99-153`
- [EVT-48] A late or replayed event is therefore dropped without a trace: for example a payment-succeeded event arriving while the order is not StockConfirmed leaves the order stuck, with no compensating action and no log at the domain level (the handler still returns success and the message is acked) — `src/Ordering.Domain/AggregatesModel/OrderAggregate/Order.cs:119-128`, `src/Ordering.API/Application/Commands/SetPaidOrderStatusCommandHandler.cs:30-31`
- [EVT-49] Subscribers that notify users (WebApp) use only the event's BuyerIdentityGuid to trigger a page refresh and then reread state over HTTP, so out-of-order events only cause extra refreshes and no wrong data — `src/WebApp/Services/OrderStatus/IntegrationEvents/EventHandling/OrderStatusChangedToPaidIntegrationEventHandler.cs:10`, `src/WebApp/Components/Pages/User/OrdersRefreshOnStatusChange.razor:27`
- [EVT-50] Ordering's stock-confirmed and paid command handlers sleep 10 s before loading the order, a simulated delay that widens the window for concurrent duplicates — `src/Ordering.API/Application/Commands/SetStockConfirmedOrderStatusCommandHandler.cs:22`, `src/Ordering.API/Application/Commands/SetPaidOrderStatusCommandHandler.cs:22`

Where data can become inconsistent
- [EVT-51] Basket cleared before the order is final: Ordering publishes `OrderStarted` in the create transaction, and Basket deletes the basket on receipt. If the order is later cancelled (grace period, stock rejected, payment failed) the basket is already gone. WebApp also deletes the basket right after `CreateOrder` and ignores the HTTP result — `src/Basket.API/IntegrationEvents/EventHandling/OrderStartedIntegrationEventHandler.cs:14`, `src/WebApp/Services/OrderingService.cs:17`, `src/WebApp/Services/BasketState.cs:107`
- [EVT-52] Stock oversell: Catalog confirms stock by reading `AvailableStock` and does not reserve it. The decrement happens only after payment. Concurrent orders can both be confirmed and paid, and the second `RemoveStock` silently removes less than requested (it removes `Math.Min`), so stock goes to 0 without error unless it is already 0 — `src/Catalog.API/IntegrationEvents/EventHandling/OrderStatusChangedToAwaitingValidationIntegrationEventHandler.cs:17-20`, `src/Catalog.API/Model/CatalogItem.cs:74-76`
- [EVT-53] Unknown product in an order is skipped by the Catalog validation, so the order can be confirmed for items Catalog does not know — `src/Catalog.API/IntegrationEvents/EventHandling/OrderStatusChangedToAwaitingValidationIntegrationEventHandler.cs:17-25`
- [EVT-54] Stock-rejected cancellation raises no domain event, so no `OrderStatusChangedToCancelled` event is published on that path: WebApp is not told, and the order shows as Cancelled only on the next read. Other cancellations publish — `src/Ordering.Domain/AggregatesModel/OrderAggregate/Order.cs:155-168` versus `142-153`
- [EVT-55] Order price snapshot vs catalog price: an order stores the price sent by the client from its own basket rehydration, and the price-change event is consumed by no useful handler (Webhooks no-op), so no other service reacts to price changes — `src/Ordering.API/Application/Commands/CreateOrderCommandHandler.cs:42-45`, `src/Webhooks.API/IntegrationEvents/ProductPriceChangedIntegrationEventHandler.cs:5-8`
- [EVT-56] Catalog price update: the DB change and outbox row are one transaction, but the event is published after commit and not retried, so a failed publish leaves the price changed with no event (EVT-28) — `src/Catalog.API/Apis/CatalogApi.cs:399-405`
- [EVT-57] Lost-update risk in Basket (blind overwrite) and in WebApp (read-modify-write from the client) — `src/Basket.API/Repositories/RedisBasketRepository.cs:37`, `src/WebApp/Services/BasketState.cs:33`
- [EVT-58] The buyer/payment-method handler saves mid-dispatch and its own code comment says the event "only works by coincidence" because it depends on the Buyer id being generated before the final save — `src/Ordering.API/Application/DomainEventHandlers/ValidateOrAddBuyerAggregateWhenOrderStartedDomainEventHandler.cs:31-33,47-51`
- [EVT-59] Event type resolution in the outbox reader matches by short name over types ending in "IntegrationEvent" in the entry assembly. A renamed or moved event type deserialises to null for stored rows — `src/IntegrationEventLogEF/Services/IntegrationEventLogService.cs:13-16,28`
- [EVT-60] OrderProcessor depends on Ordering's table and column names in SQL, so an Ordering schema change breaks the grace period silently (it swallows NpgsqlException and returns an empty list) — `src/OrderProcessor/Services/GracePeriodOrdersRepository.cs:25-27,41-45`
